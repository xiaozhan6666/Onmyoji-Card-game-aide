# 玩家资料页自动采集设计

### 点击头像补齐玩家资料

用户于 2026年10月13日确认，玩家 ID 与段位可以通过点击榜单头像查看。该功能属于第 5 阶段的自动操作，不增加数据库表；现有 player_id、grade 及图片清单引用足够保存结果。

单条观察的流程：

1. 核对当前式神、榜单页和目标行，读取该行百炼值与累计胜场，保存榜单原图及实际截图时间。处理下一行之前重新确认位置，不能只依赖最初一张截图或固定名次。
2. 点击这条目标行的头像，等待资料页标识出现、加载完成且画面稳定；用条件等待和超时处理替代无条件长时间睡眠。
3. 同一次资料页打开过程中截图，分别裁剪玩家 ID 与段位区域识别。保留 ID 的前导零；段位映射为已定义编码。未知值或低置信度不默认填充。
4. 本地记录点击的行位置、榜单截图引用、资料截图引用和两者时间。昵称、头像可作为辅助检查，但不能作为唯一身份凭据。点击后显示异常、无法确认对应关系时保留待核对，不关联到旧玩家。
5. 关闭资料页，验证返回的是原式神榜单并重新定位行。榜单刷新、名次移动或误点造成关联不确定时，丢弃本次未确认关联，重新获取该玩家的完整观察，不能按旧坐标继续点击。
6. 玩家 ID、段位、积分、胜场及来源都通过校验后，再保存完整观察。截图时间采用榜单数字的实际时间；资料页读取超时则重新采集，不能修改时间来伪装为同时取得。

资料时间差阈值沿用采集配置，目前 30 秒仅为试验参数。逐行取得新的榜单截图，避免先截图整页、再逐个打开大量资料页，导致后面玩家的段位与积分相隔过久。

### 缓存边界与失败恢复

- 首版采用每条目标观察一次资料页访问，同时读取 ID 和段位。先保证玩家身份关联正确，再通过实测决定是否优化访问次数。
- ID 作为玩家标识可以缓存；当前画面属于哪个玩家仍需验证。相同昵称、头像、页号或名次都不足以安全命中缓存。
- 同一玩家跨多个式神榜出现，也不能仅凭昵称复用身份和段位。只有独立确认是同一个 ID，且资料时间仍在允许范围内，才允许复用资料截图和识别结果；首版不依赖这种优化减少访问。
- 模型每轮只加载一次，ID 与段位共用一个 OCR 实例；同一设备只运行一个游戏操作任务。缓存、点击轨迹和资料截图时间留在采集器文件/日志，不新增数据库字段。
- 打不开资料、弹窗遮挡、返回失败或页面加载超时，按有限次数重试；仍失败则保留截图和原因，重新定位榜单后跳过该行。不能在未知页面继续点击。
- 本轮执行时间超过调度间隔时，不叠加启动新一轮；记录超时，完成当前轮后再按调度策略执行。

### 资料采集的耗时与资源预算

每次访问会增加页面打开、稳定等待、两个字段识别、关闭返回和位置复核。实际瓶颈需分别测量，当前真实榜单 OCR 试测每张约 0.36–0.54 秒（2 线程，含裁剪及诊断图保存），并未测量资料页或游戏点击耗时，不能直接据此推断完整采集速度。

估算公式：单轮时间 ≈ 榜单翻页与数字识别时间 + 资料页访问次数 × 平均单次资料访问耗时 + 重试时间。

仅作容量示例：如果选择 5 个式神、每个前 20 名，首版约需 100 次资料访问；假设每次从点击到返回核对完成平均 2 秒，额外增加约 200 秒（3 分 20 秒）。2 秒是假设，不是实测；不能承诺几秒刷新全榜。资料页访问越多，固定一个很短的采集间隔就越不现实。

第 5 阶段先测一个式神前 10 名，记录打开、等待、识别、返回各环节耗时、平均值/P95、失败率、峰值内存和整轮 CPU 使用情况。依据完整一轮的实际耗时确定式神数量、每榜人数与轮次间隔，再逐步扩展。选取固定目标榜单范围，不因为每轮谁容易点开而任意改变样本；失败项报告覆盖缺口。

资源方案优先在单个采集进程中复用轻量模型，先试 2 线程，不为每个玩家启动一个 OCR 进程。等待页面时使用低频条件检查，避免无间隔截图/OCR 轮询。CPU 2 线程限制只作用于 OCR 推理，不能限制游戏或模拟器本身的占用；额外截图也会增加磁盘用量，需要按采集量测算保留周期。

验收增加：同名玩家、相同头像、榜单实时换位、资料页加载慢、遮挡弹窗、段位变化、返回后滚动位置变化，以及本轮超时不与下一轮重叠。
